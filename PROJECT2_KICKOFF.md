## 1. Project in one paragraph

A simulator of multi-PSP (payment service provider) routing that compares **static routing** against an **adaptive router**, plus an **agent that interprets decline codes** and chooses retry, cascade, delay-and-retry, or stop. The adaptive router is a statistical problem (a bandit). The agent adds value on the long tail: ambiguous decline signals, retry timing, and plain-language explanations of decisions.

**Target user:** a payments product or operations team responsible for authorization rate and processing cost.

**Headline result to aim for (report whatever the real numbers are):**
"Adaptive routing plus decline recovery improved simulated auth rate by X points over static routing and recovered Y% of soft declines, while cutting wasted retries by Z%." Include variance across multiple seeds.

## 4. Specification

### 4.1 Simulated transaction stream
Each transaction has:
- `bin_group` (4 groups), `card_type` (2: e.g. debit/credit), `region` (3), `amount_band` (3), `recurring` (bool), `hour_of_day`
- These define a **segment**. Proposal: 4 x 2 x 3 x 3 x 2 = 144 segments. If the adaptive router cannot learn this many segments at the chosen volume, reduce segments rather than reducing volume. Confirm in `simulator-assumptions.md`.

Volume: **100k to 500k transactions per run**, seeded (`numpy.random.Generator` with explicit seed passed everywhere).

### 4.2 Mock PSPs (hidden ground truth)
- 3 to 4 PSPs with different **hidden approval probabilities per segment**, plus a **cost per transaction** (fixed + percentage).
- Suggested archetypes (confirm in assumptions doc): one cheap with a mediocre rate; one premium and strong in certain regions; one mid-tier all-rounder; optionally one that is strong on recurring but weak on one-time.
- **Drift:** at a fixed point in the run (proposal: 60% through), one PSP degrades for one region. This is the adaptation-speed test. Also consider one smaller recovery event so the router has to adapt back.

### 4.3 Objective function
Define and document explicitly (this is a core product decision):

```
value(txn) = approved * margin_per_txn(amount_band) - psp_fee - retry_cost
```
- Routers optimize **approvals net of cost**, not raw auth rate alone. Report both.
- Parameterize margin and retry cost in config; document defaults and why.

### 4.4 Decline model
Each decline has a hidden true cause, with a simplified taxonomy using **generic internal codes** (not network codes). Classes:
- **Hard** (never retry): e.g. `HARD_STOLEN_CARD`, `HARD_INVALID_CARD`, `HARD_CLOSED_ACCOUNT`, `HARD_FRAUD_SUSPECTED`
- **Soft** (retry may succeed): e.g. `SOFT_INSUFFICIENT_FUNDS`, `SOFT_ISSUER_UNAVAILABLE`, `SOFT_AMOUNT_LIMIT`, `SOFT_VELOCITY`, `SOFT_AUTH_REQUIRED`
- **Technical** (retry elsewhere): e.g. `TECH_PSP_TIMEOUT`, `TECH_NETWORK_ERROR`, `TECH_PSP_DEGRADED`
- **Ambiguous** (the agent's territory): e.g. `AMBIGUOUS_GENERIC_DECLINE`, `AMBIGUOUS_DO_NOT_HONOR`, where the true cause is hidden and the response code alone does not settle it. Context (segment, history, PSP health, time since last attempt) shifts the likelihood.

For every decline, the simulator holds hidden retry-success probabilities per action: `retry_same_psp_now`, `retry_same_psp_delayed`, `cascade_to_<each other PSP>`, `stop`. The **oracle best action** is the one with the highest expected net value. Hard declines have ~0 success for every action; retrying them has a cost (and in the metrics counts as a **wasted retry**).

### 4.5 Routers (one interface, four strategies)
```python
class Router(Protocol):
    def route(self, txn: Transaction, state: RouterState) -> PSPChoice: ...
    def observe(self, txn: Transaction, psp: str, outcome: Outcome) -> None: ...
```
1. **Static primary with failover:** fixed primary PSP, fail over to a fixed secondary on technical errors only.
2. **Rule-based by segment:** hand-written rules mapping segment to PSP (written from the *observable* first part of the run, not from hidden truth, to keep it fair).
3. **Adaptive router:** Thompson sampling with Beta priors per (segment, PSP), optimizing expected net value. Include a **per-PSP traffic cap** and a minimum exploration floor as explicit guardrails. If segment-level learning is too sparse, use hierarchical backoff (segment -> region/BIN group -> global) and document it.
4. **Adaptive + decline-recovery agent:** router 3 plus the agent handling declines.
Also implement an **oracle router** (knows hidden truth) used only as the benchmark for regret.

### 4.6 Decline-recovery agent
- Input: response code, transaction segment, decline history for this customer/transaction, PSP health stats, time since last attempt.
- Output (structured JSON): `action` in {`retry_same_now`, `retry_same_delayed`, `cascade`, `stop`}, `target_psp` if cascade, `delay_seconds` if delayed, `confidence`, and a short `explanation`.
- **Tools (deterministic, read-only):** `get_decline_history`, `get_segment_stats`, `get_psp_health`, `estimate_retry_success`.
- **Selective calling (cost control):** a deterministic rules layer handles clear cases (all hard declines -> stop; clear technical errors -> cascade). The agent is called **only** when the rules cannot classify with confidence. Log the agent call rate.
- **Guardrails:** the agent must never recommend retrying a code classified hard by the rules layer (enforced in code, not only in the prompt). Any invalid or unparseable output falls back to the rules layer's default action. Log every fallback.
- Cap spend: configurable max agent calls per run; cache identical (code, segment bucket, context bucket) calls.

### 4.7 Metrics
| Metric | Definition |
|--------|-----------|
| Authorization rate | Approved / attempted, per router, overall and per segment |
| Net value per transaction | Using the objective in 4.3 |
| Net cost per approved transaction | PSP fees plus retry costs divided by approvals |
| Regret vs oracle | Gap in cumulative net value to the oracle router over time |
| Adaptation speed | Transactions needed after the drift event to shift traffic away from the degraded PSP (define threshold, e.g. share of affected-region traffic to that PSP falls below X% of its pre-drift share) |
| Retry efficiency | Recoveries per retry attempt; **wasted retries on hard declines** |
| Soft decline recovery rate | Recovered soft declines / total soft declines |
| Agent decision quality | Agent action vs oracle best action (exact match, and value gap) on ambiguous declines |
| Agent cost | Calls per 1,000 declines, tokens, latency, fallbacks |
| Segment guardrail | Per-segment auth-rate change vs static; flag any segment that gets worse while the average improves |

All results reported as **mean and spread (e.g. min/max or 95% interval) across at least 10 seeds**.

## 5. Eval principles
- Build the metric code and baseline comparison **before** the adaptive router and agent.
- Use separate seed sets: **dev seeds** (for tuning) and **frozen eval seeds** (for reported results, never tuned on). Record the frozen seeds in `evals/seeds.json` in Phase 2.
- Report baselines next to every result: static, rule-based, oracle, adaptive, adaptive+agent.
- Report agent cost and latency, not only accuracy.
- Include one **failure analysis**: five real cases where the agent chose badly, why, and what would fix it.
- Include an agent ablation: adaptive router with rules-only decline handling vs with the agent, so the agent's marginal value is visible.
